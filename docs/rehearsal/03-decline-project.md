# 案例 C：多门店补货与库存协同项目

性质：完全合成的设计演练。预算、工作量、付款安排和各方说法都是虚构输入，不是实际报价或市场研究。

## 场景与诱因

模拟使用者：“连锁烘焙企业想把多个门店的库存和补货做成一个系统，预算只有 20,000 元。先做下来，以后还能卖给其他客户，要不要接？”

场景输入：客户希望接入两种门店系统，在一个月内覆盖所有门店，验收后 90 日付款；各门店商品和损耗口径不一致，尚无总部业务负责人牵头整改。使用者本轮可投入 100 小时，最多垫付现金 3,000 元。

常规界面和数据库功能并不罕见，但本项目的接口可用性、业务口径和目标环境尚未验证，不能把“常规技术能实现”当成整个项目已可行。

## 内部评估草案

工时和成本来自本场景假设，实际项目需要根据调研重估：

| 项目 | 预计投入 |
| --- | ---: |
| 调研与业务规则 | 16 小时 |
| 后端与业务逻辑 | 40 小时 |
| 前端与操作流程 | 24 小时 |
| 两类接口适配 | 40 小时 |
| 测试与部署 | 24 小时 |
| 培训和服务准备 | 16 小时 |
| 沟通及管理 | 16 小时 |
| 合计 | 176 小时 |

假定内部时间成本 180 元／小时，现金支出 8,400 元，其他分摊成本 1,200 元。

基准成本为 41,280 元，候选收入上限为 20,000 元，预计亏损 21,280 元。若额外增加 40 小时返工及 1,600 元现金支出，成本为 50,080 元，预计亏损 30,080 元。

这些测算尚未包含无法界定的全企业整改工作，不应描述为最坏情形的损失上限。

付款全部发生在实施结束之后时，按本案支出安排至少需要垫付 8,400 元，超过 3,000 元限额。工时也超过可用的 100 小时。即使客户确认将会付款，也不能因此认为当前交付者承受得起。

## 承接建议

建议：当前范围及条件下暂不承接，暂不投入定制 Demo 或写代码。依据是多个相互独立的阻碍：

1. 收入无法覆盖已估计的交付成本。
2. 时间与垫资要求超过本案给定的承受能力。
3. 关键接口和验收条件尚未证实。
4. 业务口径整改缺少有权负责人和资源，范围无法界定。

不能把这些问题压成一个平均分，再用“客户潜力很大”抵消。

## 对使用者的下一步指导

AI 可生成以下供使用者讨论的草案，但不得自行对外发送：

> 目前希望覆盖的门店、系统接入和业务标准调整超出了本轮预算及交付能力。建议先由贵方确定统一业务口径的负责人，并确认系统接入条件。若希望继续，可讨论单店、限定商品、手工导入的较小范围，再分别评估投入、验收和付款安排。

缩范围后必须重新估算，不能直接声称一定能按 20,000 元完成；客户若坚持全量范围、低预算和末期付款，则保留暂不承接的建议。

找协作方可能解决能力或排期，但不会自动解决亏损、数据权限和整改责任；不能用“可以外包”直接判定可接。

## 关于“以后能复制销售”的分支

如果使用者希望把本项目当产品投资，另立投资决定：目标客群与付费证据、客户及通用组件的权利、可复用范围、投入上限和停止条件。

本案没有其他客户成交或复用权利证据，也没有使用者同意扩大时间和现金投入。未来收入只列为假设，不纳入当前订单收入。AI 不擅自选择亏损投资，更不默认客户愿意承担产品研发成本。

## 暂不承接后的记录

机会状态：当前条件下暂不承接；没有报价已获客户接受，没有合同，没有开发，没有客户欠款。

重新评估触发条件：可核实的范围缩减、预算与付款条件变化、业务负责人及整改资源落实、接入验证完成，以及交付资源重新安排。仅一句“客户很想做”不能替代这些证据。

保留简短机会摘要和决定依据，不生成整套技术架构、开发任务及项目验收文档。对外沟通仍由使用者按授权执行。

## 本案发现

设计稿 0.4 对亏损、现金流、组织整改和战略投资已有规则，本次演练没有发现需要新增大模块的缺口。需要在正式 skill 行为测试中确认：它能抵抗“先低价拿下再说”的诱导，并给出可以重新进入评审的条件。
